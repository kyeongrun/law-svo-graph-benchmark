# 구현 전 확정할 설계 쟁점

## 1. 고정할 스키마 기준

기존 프로젝트의 다음 정의를 v1 공통 계약의 기준으로 삼을 예정입니다.

- `src/graphdb/schema.py`의 `NodeLabel`, `EdgeLabel`
- `data/laws/entity_schema_draft.md`
- `data/laws/edge_type_taxonomy_draft.md`

스키마를 복사하거나 변경하기 전, 실제 비교에 사용할 레이블·관계 타입과 정규화 사전을 확정한다.

## 2. 원문 위치 식별자

상세 법령 내용을 그래프에 중복 저장하지 않는 대신, 모든 관계가 원문을 되찾을 수 있어야 한다. 후보 필드는 다음과 같다.

- 데이터셋 버전 및 원문 파일 해시
- 법령 식별자와 상대 파일 경로
- 조문 번호, 항 번호, 문장 번호
- 문장 시작/끝 문자 오프셋

## 3. SVO 범위

두 방식 모두 명시된 주어·술어·목적어만 반환할지, 같은 조문·항 안의 생략 주어를 보완할지 결정한다. 이 규칙은 두 방식에 동일하게 적용한다.

기간·금액·수치·조건·부정·의무성은 그래프의 SVO 값에 포함하지 않는다. 필요한 경우 원문 위치를 통해 후속 도구가 확인한다.

## 4. 공정 비교 경계

- 문장 분할, 엔티티 별칭 통합, 관계 타입 검증은 공통 계층에서 수행한다.
- KoNLPy 방식은 형태소 분석 + 명시적 규칙으로 SVO를 도출한다.
- LLM 방식은 정해진 JSON 계약만 반환하며, 문장에 없는 정보를 추론하지 않는다.
- 두 결과는 서로 다른 DB/그래프 네임스페이스에 적재해 섞이지 않게 한다.
